auth-lib: users, roles and permissions, configured per client

A Go library for user, role and permission management and sign-in, extracted from PPE-next2 and shared by every app. Each app declares its permissions as a module. Each client's profile picks the modules of its app set and defines the roles across them. Roles are granted everywhere or on particular objects (object-based RBAC). It's the in-process step before auth-proto, which will be built on top of it.

repo: remis-libs/auth-libdate: 2026-11-27basis: PPE-next2's user, session, role and security packagesfirst client: Gavort (PPE-next2 + Crew)

01Goals and decisions

  • One copy. The users, sessions, roles, permissions and security log that PPE-next2 and PPE Crew each carry today become one library with its own tests.
  • Configured, not forked. What differs between clients and app sets (modules, built-in roles, languages, session limits) is configuration, checked at start-up and in CI.
  • Smaller apps. Auth leaves PPE's cmd/api and four packages, and stops needing a migration for every new permission.
  • Object-based roles. A role may be granted on one client, project or company and what is under it, not only system-wide (Object scopes).
  • A small surface. Everything lives in internal/ except the few names an app must touch; the exported API is checked in and reviewed (Library and API).
  • A path to auth-proto. The same services later run behind auth-proto's OAuth layer, with the database levels as stepping stones.

04Modules and permission keys

a module, declared by the app
var Projects = authlib.Module{
	Key:   "projects",
	Label: "modules.projects", // the app's dictionary key
	Permissions: []authlib.Permission{
		{Key: "projects.manage", Group: "projects"},
		{Key: "projects.assign", Group: "projects"},
		{Key: "projects.override", Group: "projects", Requires: []authlib.Key{"projects.assign"}},
	},
	Apps: []authlib.AppEntry{{Slug: "crew", AnyOf: []authlib.Key{"projects.manage", "projects.assign"}}},
}

// Typed keys for routes: rt.restricted("POST /api/v1/assignments", h.assign, perm.ProjectsAssign)
const ProjectsAssign authlib.Key = "projects.assign"

Rules

  • A key is unique in its app set. The start-up check refuses a duplicate, naming both modules.
  • Platform keys are reserved: users.read, users.manage, roles.manage, security.read. A module may not declare them.
  • New modules' keys start with their module key (projects.*). Crew's keys already do: people.*, competence.*, projects.*.
  • PPE's existing keys are kept as they are (orders.delete, sim_cards.manage). Its modules mark them Legacy: true, which exempts them from the prefix rule. Tokens, session.can() and permissions.ts don't change.
  • Crew's users.manage becomes the platform's. The two meant the same thing.
  • Removing a key from a module leaves it dormant: no role grants it any more, but rows stay, so a revert restores it.

  • Where it lives. In the repository that deploys the client (PPE-next2's deploy/clients/gavort/), mounted read-only, its path in API_ACCESS_PROFILE. One build serves every client.
  • What it replaces. PPE's API_SESSION_*, API_RECENT_SIGN_IN, API_JWT_TTL, API_AUTH_EVENTS_RETENTION, builtin.go and the permission lists in migrations. Secrets (API_JWT_SECRET, later signing keys) stay in the environment.
  • Start-up check, which refuses to start and names the problem:
    • every module named exists in the binary, and every key in a role is in the catalogue
    • every key's Requires is granted alongside it
    • exactly one guarded role, holding users.manage and roles.manage
    • add-on roles are not implied by grant: all
    • role ids and keys are unique, and a built-in role's id never changes between versions
    • languages are ones the apps' dictionaries have
  • The same check in CI: api -check-access deploy/clients/gavort/access.yaml, run against the built binary's modules, so a bad profile fails the build, not the deploy.
  • /ready reports the profile's client and hash; /admin/ System shows them.

06Roles

Built-in roles

  • Defined in the profile with a fixed id and key; names and descriptions come from the apps' dictionaries by key, as today.
  • Locked: at start-up their permissions are set to the profile's, under a lock, with an audit event per change. They can't be edited on Roles & permissions.
  • A built-in role missing from a newer profile is not deleted: it becomes a custom role, so users keep it.
  • Before locking, Phase 2 copies production's current built-in sets into the profile, so locking changes nothing on day one.

Custom roles

  • Rows, edited by administrators, as today. They may grant any catalogue key, within containment.
  • Keys from a module the profile turns off stay in the row, dormant, and are left out of tokens.

Rules carried over from PPE

  • Add-on: never implied by another role, Administrator included (Equipment Assignments, Personnel Documents, Employment Documents, Testers).
  • Containment: a role or user may be changed only by someone holding everything it grants, on that scope or above.
  • Guarded: at least one active user always holds the guarded role, checked after each change under an advisory lock.
  • No one takes users.manage or roles.manage from themselves.

Apps a user may open

  • A module lists the apps it serves and their entry permissions (AnyOf).
  • auth.AppsFor(principal) answers which apps the user may open, so the launcher's rule and a future app switcher share one source.

07Object scopes

Roles are object-based: a user holds a role on a scope, either everywhere (global, as today), on one object, or on everything under an object. A check names the object it is about, so a permission applies to particular items rather than system-wide. Today's role holdings become global grants, so nothing changes for PPE until a module uses scopes.

TermMeaningDefined in
Object typeA kind of thing access can be limited to, with an optional parent type: client → project, company → employeeThe module
ObjectA type and an id (project, P-114). The object itself is the app's data; the library stores only its type and idThe app's database
ScopeWhere a grant applies: global, or one object and everything under itEach assignment
AssignmentA user holding a role on a scope, with who granted it, when, and an optional expiryThe library's database
Check"May this caller do key to object?" True when an unexpired assignment's role grants the key and its scope is global, the object, or one of the object's ancestorsThe library, at run time

Declaring object types and where permissions apply

Crew's projects module
var Projects = authlib.Module{
	Key: "projects",
	ObjectTypes: []authlib.ObjectType{
		{Name: "client"},
		{Name: "project", Parent: "client"},
	},
	Permissions: []authlib.Permission{
		{Key: "projects.manage", Group: "projects", On: "client"},
		{Key: "projects.assign", Group: "projects", On: "project"},
		{Key: "projects.override", Group: "projects", On: "project", Requires: []authlib.Key{"projects.assign"}},
	},
}
  • A permission without On is global only (settings.manage, users.manage). A permission with On: "project" may be granted globally (every project), on a client (its projects), or on one project.
  • Object type names are unique in the app set, like keys; a parent must be declared in the same module or one the module depends on.

Roles granted on a scope

gavort/access.yaml, roles
  planner:          { id: …, grant: [people.manage, projects.manage, projects.assign] }   # global only, the default
  client-planner:   { id: …, grant: [projects.manage, projects.assign], assignable_on: [global, client] }
  site-coordinator: { id: …, grant: [projects.assign], assignable_on: [project] }
  • assignable_on lists the scopes a role may be granted on; the default is [global].
  • The start-up check refuses a role assignable on a type when one of its permissions doesn't apply there: people.manage is global only, so planner can't be granted on a client.
  • Containment per scope: someone may grant a role on Shell only when they hold everything it grants on Shell or above.
  • The guarded role (Administrator) is always global. Add-on roles may be scoped. Grants may expire (expires_at), for temporary access.

Checks in the app

one object, and a list
// The route's gate passes when the caller holds the key anywhere; the handler then asks about the object.
rt.restricted("POST /api/v1/projects/{id}/assignments", h.assign, perm.ProjectsAssign)

ok, err := auth.Can(ctx, p, perm.ProjectsAssign, authlib.Object{Type: "project", ID: id})
if !ok { return authlib.ErrForbidden }

// A list: everything, or the objects to filter by.
in, err := auth.Scopes(ctx, p, perm.ProjectsAssign, "project")
if !in.All() {
	rows, err = q.ProjectsWithin(ctx, in.IDs("client"), in.IDs("project"))
	// WHERE client_id = ANY($1) OR id = ANY($2)
}
  • Parents come from the app. Config.Ancestry is a function that answers an object's ancestors (a project's client). The library calls it only when the caller holds a scoped grant of an ancestor type, and caches the answer for the request. Objects are never copied into the library.
  • Lists are the hard part of object-based access. Scopes returns All for a global grant, or the ids per type on the path down to the type asked for, and the app filters its own query with them.
  • Deleting an object: the app calls auth.Forget(ctx, obj) to drop the assignments on it. An assignment left on an unknown id grants nothing.
  • Where checks run. Global keys stay in the access token, so p.Can(key), session.can() and PPE's routes work as today. Scoped grants are never put in tokens. They are loaded on the server on the first scoped check of a request and cached per user and access_version. The version is one indexed read per such request and moves with every grant or removal, so a removed grant stops working on the next request.

08Library and API

Everything starts in internal/. Go refuses any import of an internal package from outside the module, so apps can't depend on the library's services, stores, tokens or handlers. Each exported name is a promise that must be kept across versions, so the library exports only what an app has to touch: declaring its permissions, wiring the library in, registering its routes, and asking who the caller is and what they may do.

Rules for the public surface

  • New code goes into internal/. Moving a name out needs a reason in the pull request, and an app that can't work without it.
  • No exported signature mentions an internal type. A test walks the exported API with go/types and fails if one does.
  • Values handed out are copies: slices and maps are cloned, and Principal and UserInfo have no pointers into the library's state.
  • Principal's fields are unexported; it is read through methods, and only the library and authtest make one.
  • Store is sealed (an unexported method), so apps choose a store but can't implement or inspect one.
  • Interfaces the app implements stay small: Registrar has three methods; the other ports are single functions.
  • Errors are the fixed set above. Messages never carry SQL, table names, hashes or tokens.
  • No global state and no init; time comes from Config.Now.

Contracts outside Go

  • HTTP: the routes' paths and JSON are public, since the apps' frontends call them. They stay PPE's in v1, are listed in docs/http.md, and are pinned by golden JSON tests.
  • Database: the tables are the library's own. Apps may reference auth.users(id) in foreign keys and read the view auth.directory (id, email, name, language, active), and nothing else. Changing either is a breaking change.
  • Profile: the file format is versioned (version: 1); an unknown field is refused.
  • Audit events: their names (user.*, role.*) and snapshots are public, grants and removals carrying their scope,, as apps keep them in their trails.
Keeping it small. api.txt holds the exported API as go doc -all prints it. CI fails when the API changes and api.txt doesn't, so every change to the surface shows up in review. Before a release tag, apidiff against the previous tag decides the version: a breaking change needs a major version from v1 on. The library imports no app package; a test fails on any remisb/ppe-* import.

  • Migrations: the library embeds its own, with its own version table auth.schema_migrations, run by api -migrate-auth before the app's. PPE's make migrate, deploy/migrate.sh and /ready call it.
  • Moving into auth: the first library migration is a baseline. When public.users exists, it moves the six tables with ALTER TABLE … SET SCHEMA, which keeps every foreign key, index, trigger and row. On an empty database it creates them.
  • Grants: the library ships grants.sql for its schema, taking the app's role name (ppe_app) as a parameter. Append-only auth_events and its purge function move with it.
  • Assignments: role_assignments(user_id, role_id, object_type, object_id, granted_by, granted_at, expires_at) replaces user_roles, one row per user, role and scope (a unique index over the scope with empty values for global), with an index on (object_type, object_id) for Forget. users.access_version moves with every change. P2's migration, still one of PPE's at L0, turns each user_roles row into a global assignment.
  • Public objects: apps may reference auth.users(id) in foreign keys and read the view auth.directory; every other table, column and function is the library's own and may change in any release. PPE's 15 Go files that join users for names read auth.directory instead.
  • Tests: authtest.Reset(tx) empties the library's tables and syncs built-ins again, replacing TRUNCATE users CASCADE plus role.EnsureBuiltins.
  • SQLite (later, an option): internal/store/sqlite, chosen with authlib.SQLite(db, …), on modernc.org/sqlite (pure Go: WAL, BEGIN IMMEDIATE for FOR UPDATE and the advisory lock, UTC text times, paired migration folders), with one contract test run on both stores. It applies at L2, or to an app that is entirely on SQLite.

10What moves

Out of PPE-next2

  • internal/domain/{user,session,role} and internal/security into the library.
  • cmd/api/auth.go, auth-cookie.go, auth-routes.go, user-routes.go, role-routes.go, security-routes.go into internal/httpapi, with their tests; PPE registers them with auth.Routes(rt).
  • role/permission.go splits: the engine into the library; PPE's keys, groups and requirements into a new internal/perm with its modules. The 64 role.* names become perm.*: mechanical.
  • role/builtin.go into deploy/clients/gavort/access.yaml.
  • New permissions stop needing a migration.

Out of PPE Crew

  • internal/platform/iam is deleted; Crew's API uses the library.
  • Its keys move into three modules, people, competence and projects, unchanged except users.manage, now the platform's.
  • Its built-in roles (planner, coordinator, viewer) move into Gavort's profile once its modules join PPE's binary; until then, into a profile of its own.
  • API_SHARED_USERS_DB_DSN stays until the merge.

Stays in each app

  • The permission keys and modules, and every check on a route.
  • The audit trail and its seals.
  • The objects themselves and their parents (answered through Ancestry), ownership rules and field visibility (see Object scopes), and which employee a user is.
  • Screens: Sign in, Account, Users, Roles & permissions, Security (see Frontend).

11Frontend

  • v1 changes no screen. The routes keep their paths and JSON, so @ppe/app-shell's sign-in, Confirm your password and session code, and Administration's Users, Roles & permissions and Security, work as they are.
  • Roles & permissions marks built-in roles read-only (decision 4) and groups permissions by module, from GET /api/v1/roles/catalogue.
  • Users shows each grant with its scope; the screen asks the app for the object's name. A scope picker appears only once a module declares object types (Crew in P4).
  • @ppe/api-client's permissions.ts stays hand-written. The Go test that compares it now reads the catalogue built from the modules.
  • Later: @remisb/auth-react with Sign in, Confirm your password, Account and the Users and Roles screens, for the apps to share. Labels stay in each app's dictionaries, by key.

13Testing

In the library

  • The services' tests from PPE, moved with them, on fakes: refresh rotation and grace, limits, containment, the guarded role, the email limit.
  • Store tests on real Postgres, in their own database, in parallel, independent of any app's test lock.
  • Profile checks: table tests of good and bad profiles and modules.
  • Built-in sync: adds, removes, keeps dormant, writes one event per change, is a no-op the second time.
  • Object scopes: table tests of Can (global, the object, an ancestor, another branch, another type, expired, a dormant key); a property test that filtering by Scopes keeps exactly the objects Can allows; containment per scope; assignable_on in the start-up check; a grant's removal seen on the next request; Forget.
  • Migrations: the baseline on an empty database and on a copy of PPE's tables.
  • Import boundaries: no app package; no net/http outside internal/httpapi, the root package's Middleware and muxauth.
  • The public surface: api.txt matches go doc -all; no exported signature names an internal type; every exported name has an example.
  • HTTP contract: golden JSON for every route's answers, so a change to a shape is seen.

In the apps

  • Apps' handler tests make callers with authtest.Principal(userID, keys…) instead of signing tokens.
  • PPE keeps TestRoutePolicy and TestSeededRolesKeepPolicy, now fed by the profile.
  • A golden test: gavort/access.yaml gives the role → permission sets recorded from production.
  • permissions.ts against the catalogue, as today.
  • e2e unchanged; its global setup seeds through the library.
  • Crew: for each scoped role, its lists and checks stay inside the scope.

14Risks

RiskMitigation
A bad profile stops the API at deploy-check-access in CI on the same binary; prod-up waits for /ready before replacing Caddy, so the old API keeps serving
Locking built-ins drops an edit made in productionP2 copies production's sets first and the golden test proves equality; a profile may still mark a built-in seeded (created once, then editable) for a client who wants that
The library grows to fit every app's differencesA small core; API tokens and invitations as optional packages later; an app's quirks stay in the app through BeforeDelete and similar single-function options; new exports need a reason, and api.txt shows every one in review
Changes spanning library and app need two releasesgo.work locally; tagged versions; the library's CI runs PPE's auth tests against the change before tagging
Another private module in the image buildsThe same .github-token secret as dbbackup and pdf-mini, with read access added; or make the repository public, as it holds no secrets
Lists slow down with many scoped grantsScopes returns ids per type, cached per user and version; if one user ever holds thousands, a public view of a user's scopes lets the app join in SQL instead
A wrong Ancestry grants too much or too littleEach app tests its Ancestry against its data; the library refuses a parent of the wrong type and stops at a depth limit

15Not in v1

  • SQLite, API tokens, invitations, email sign-in codes (later).
  • Relation-based rules (ownership) and conditions on values (see Object scopes).
  • Groups or teams holding roles.
  • A separate auth database and the users mirror (L2).
  • A new token format: v1 keeps PPE's HS256 access tokens and refresh cookie as they are.
  • Shared React screens (@remisb/auth-react).
  • Several clients in one database.

16Open questions

  • Profile format. YAML is easy to read and review; JSON needs no parser dependency. YAML is proposed, through a small, strict decoder that refuses unknown fields.
  • Crew's merge timing. P4(b) waits for Crew's contexts to move into PPE's binary. Until then Crew runs the library with its own profile.
  • Public or private repository. Public removes a build secret; private matches dbbackup and pdf-mini.
  • Groups. Should a team hold assignments, so granting a client's planners is one row? Not in v1; the assignment's holder can become a user or a group later.
  • Object names on Users. One endpoint per object type in the app, or a Describe function the library calls? To settle in P4 with Crew's screen.
  • Server sessions. The guidelines prefer opaque server sessions to JWTs. The library is where that change would be made once for every app. Which phase should it be?
